# Internal Workflow: Project Setup

Create the initial Governance/Product pair. Connecting an existing pair belongs to `project-activation.md`.

1. Confirm the new project's identity, destinations, portable Governance identity/source arrangement and workstation paths. Existing repositories are not replacement targets; route an existing-pair request to Project Activation.
2. Interview for the required initial content and show the generated artifacts for review. The Constitution may contain no substantive rules; do not invent foundational requirements from tentative goals. Create a separate non-normative Governance README explaining requirements, Discovery Charter/Repo, Discovery Report with Findings and Conformance Proofs, Governance Proposals and separate Governance Adoption. Link available artifacts and public routing; describe unimplemented handlers as manual or unavailable. Create additional documents only when needed.
3. Create the Governance repository and its approved initial commit, preserving normal Git identity, signing and hooks.
4. Create Product and its read-only Governance submodule at that first Governance commit, then create Product's approved initial commit. Apply the authoritative plan's narrow initialization contract; do not create remotes, hosted repositories, or a Discovery Repo.
5. Generate missing role instructions and the applicable approved metadata using the authoritative plan's layout. Validate the created pair and its initial Governance relationship.
6. Save Local Project Configuration and summarize the initial state and generated changes.
7. On interruption, use the approved Resume/Roll back contract; recognize completed initial commits and preserve unexpected user changes rather than repeating or resetting work.

Project Setup is the initial creation activity. Product's later Governance Adoption and a workstation's Project Activation are separate workflows. Reference descriptions do not authorize running implementation chunks.
